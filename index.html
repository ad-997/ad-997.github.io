DEEP DIVE — RELAYOPS

Reliability you can
put to the test.

A working webhook reliability lab with reproducible experiments, recorded outcomes, and clear engineering tradeoffs.

The failure is the feature.

A receiver can time out after an event is accepted. A producer can submit the same event twice. A worker can crash between delivery and acknowledgment. RelayOps makes these states explicit.

  1. 01

    React → Spring Boot

    An operations dashboard submits validated dispatch requests and exposes event state and attempt history.

  2. 02

    FastAPI → durable SQL queue

    Unique idempotency keys suppress duplicates. Transactions and expiring leases coordinate workers and recover interrupted jobs.

  3. 03

    Signed delivery → controlled receivers

    HMAC signatures identify payloads. Exponential backoff with jitter handles transient failures; exhausted events enter the dead-letter queue.

  4. 04

    Investigate → replay

    Attempt history records status, outcome, and duration. Manual replay preserves the earlier history for investigation.

Tradeoffs & boundaries +

At-least-once delivery can produce duplicate receiver calls after a crash; consumers must deduplicate event IDs. The local edition uses registered test receivers, not unrestricted third-party URLs. SQLite was measured; the MySQL deployment recipe needs its own validation. Authentication, rate limiting, endpoint provisioning, monitoring infrastructure, and load testing are further work before public production use.
